# Product Requirements Document (PRD) Framework

This skill teaches you how to draft a structured Product Requirements Document. A PRD is the single source of truth for a feature or product, aligning the team on the "Why", "Who", and "What" before implementation begins.

## PRD Template Structure

When asked to draft a PRD, structure your output using these sections:

### 1. Title & Metadata
*   **Feature Name:** [Name]
*   **Target Release:** [Date/Sprint]
*   **Status:** [Draft / In Review / Approved]

### 2. Problem Statement
*   What is the specific problem we are trying to solve?
*   How does the user experience this problem today?
*   Why is it urgent or important to solve this now?

### 3. Objectives & Key Results (OKRs)
*   What does success look like for this feature?
*   **Metric 1:** [e.g., Increase conversion rate by X%]
*   **Metric 2:** [e.g., Reduce customer support tickets related to Y by Z%]

### 4. Target Audience (Who)
*   Who are the primary users?
*   What are their specific constraints, needs, or environments?

### 5. Proposed Solution (What)
*   High-level overview of the solution.
*   **Core User Flows:** Step-by-step description of how the user will interact with the feature.
*   **In Scope:** Specific features and behaviors to build.
*   **Out of Scope:** Features explicitly excluded from this release to prevent scope creep.

### 6. Technical & Design Requirements
*   Dependencies on other systems or teams.
*   Security, performance, or compliance constraints.

### 7. Launch & Rollout Plan
*   Phases (e.g., Internal Dogfooding -> Beta -> GA).
*   GTM strategy or user communication.

## Instructions for Product Manager (Planner)
Use this template when rewriting or expanding the `GOAL.md` or when instructed to formally document a new feature request. Ensure you validate assumptions before writing the final draft.
